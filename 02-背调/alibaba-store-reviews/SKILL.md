# Alibaba 店铺评论抓取

抓取阿里巴巴国际站（`*.alibaba.com` 店铺小站）的 Feedback（买家评论）页，按标准字段结构化后存档进 wiki，供营销素材（真实评价引用）、独立站内容、竞品调研使用。

**核心原则：宁可留空，不可编造。** 抓不到的字段按下方"字段获取难度与兜底规则"如实标注，不得为了凑齐字段瞎猜或编造数值/文本——这是本项目一贯的规则（参见 `schema/products-schema.md` 反复强调的"没有可验证数据就留空"）。

---

## 输入解析

用户给的链接可能是以下任意一种：

- 店铺首页：`https://<store>.en.alibaba.com/`
- Feedback 页直链：`https://<store>.en.alibaba.com/company_profile/feedback.html`
- 店内某个产品详情页：`https://<store>.en.alibaba.com/product/xxxxx.html`

**处理步骤**：
1. 从链接的子域名提取 `<store>`（如 `fouwell.en.alibaba.com` → `fouwell`），作为店铺目录 slug。若链接是产品页或其他形式导致提不出干净的子域名，先访问该链接，从页面跳转/店铺信息里找到真正的店铺子域名。
2. 拼出 Feedback 页地址：`https://<store>.en.alibaba.com/company_profile/feedback.html`
3. 打开该页，从页面标题/公司信息区读取**店铺真实名称**（用于输出文件里的"店铺名称"字段，slug 和真实名称可能不同，如 slug=`fouwell`、真实名称="Fuzhou Fouwell Technology Co., Ltd."）

## 抓取方法（按可靠性从高到低尝试）

Alibaba 店铺小站的 Feedback 页在不同店铺/不同时期实现方式不完全一致，按下面顺序尝试，用第一个能稳定拿到"评论编号/买家名称/评论时间/评论型号/型号链接"这些结构化字段的方法：

### 方法 A（优先）：找到评论列表的数据接口

用浏览器自动化工具（本环境已装的 `ego-browser` / `browse` / `connect-chrome`，选一个可用的）打开 Feedback 页并翻到第 2 页，同时观察网络请求（Network / XHR）。阿里的店铺小站页面常见做法是评论列表由前端 JS 拉取一个返回 JSON 的接口（分页参数通常是 `page`/`pageNum` 之类）。如果找到这个接口：

- 直接改分页参数依次请求全部页，拿到的是**结构化 JSON**，通常已经按"一条评论对应一个订单/型号"整理好，字段比解析渲染后的 HTML 更完整更可靠（评论 ID、买家名、日期、型号、链接大概率都在里面）。
- 这是最省事也最准的路径，优先用。

### 方法 B：结构化解析渲染后的 DOM

找不到干净接口时，用浏览器工具逐页打开 Feedback 页，**对评论列表容器做结构化提取**（按评论卡片/列表项一个个取字段），而不是把整页转成纯文本再用正则瞎猜边界。每条评论卡片内通常包含：买家名/头像、国家（国旗+文字）、Supplier Service 星级、On-time Shipment 星级、评论时间、评论文字、以及该评论关联的型号（图片缩略图+型号文字+链接）。按卡片为单位取字段，能保证"评论文字"和"型号"的对应关系不错位。

### 方法 C（兜底，已知精度较低）：WebFetch 转文本 + 规律切分

如果方法 A/B 都不可行（比如环境里没有可用的浏览器工具），退化成用 WebFetch 把每页转成文本，用结构规律（例如"评论文字后紧跟一个纯数字行"）粗略切出候选评论——2026-09-12 对 Fouwell 自家店铺的抓取就是这么做的，存档在 `wiki/marketing/_alibaba-reviews/fouwell/`（已标注为 legacy）。这种方法**拿不到评论编号/买家名/评论时间/评论与型号的对应关系**，产出必须在店铺 README 里如实注明"方法C，以下字段无法可靠获取"，不能假装数据完整。

## 分页与翻页终止条件

Feedback 页面按"每页 N 条评论"分页。抓取时：
1. 先确定总页数（页面上通常有页码或"共 X 页"提示）
2. 从第 1 页抓到最后一页，每抓完一页检查是否还有"下一页"可点/该页返回是否为空
3. 页与页之间间隔 1-2 秒再请求，避免短时间高频请求触发风控
4. 如果中途遇到验证码或明显的反爬拦截页面，**停止抓取，如实告知用户**（已抓到第几页/多少条），不要尝试自动过验证码或用其他手段绕过检测——这类拦截该由用户人工处理或换个时间再试

## 标准数据字段

每条评论输出以下字段（对应用户要求的标准结构）：

| 字段 | key | 说明 |
|------|-----|------|
| 店铺名称 | `store_name` | 店铺真实名称，同一店铺内所有记录相同 |
| 评论编号 | `review_id` | 见下方"字段获取难度"——多数情况下阿里页面不展示对外评论ID，退化为抓取时生成的序号 |
| 买家名称 | `buyer_name` | 页面展示的买家名（常打码，如 `M***n`），未展示则留空并标注 |
| 买家国家 | `buyer_country` | 国旗对应的国家/地区名 |
| Supplier Service | `supplier_service_stars` | 分项星级，整数或含小数的评分（视页面展示精度） |
| On-time Shipment | `on_time_shipment_stars` | 分项星级 |
| 评论时间 | `review_date` | 尽量转换成 `YYYY-MM-DD`；页面只给相对时间（如"3 months ago"）时，原样保留并标注是相对时间 |
| 评论型号 | `reviewed_model` | 该评论关联的产品型号/标题；确实无法判定归属时填 `[无法确定型号]`，不要瞎猜 |
| 星级 | `overall_stars` | 总体评分；页面没有单独展示总分时，用 `(supplier_service_stars + on_time_shipment_stars) / 2` 四舍五入推算，并在该条记录加 `overall_stars_derived: true` 标注这是推算值 |
| 评论内容 | `review_content` | 原文语言原样保留，不翻译、不改写 |
| 对应型号的链接 | `model_url` | 型号关联的产品详情页链接（绝对URL） |

**字段获取难度与兜底规则**（诚实记录，来自 2026-09-12 那次实际抓取踩过的坑）：
- **评论编号**：阿里 Feedback 页通常不展示平台原生评论 ID。方法A的接口如果返回了内部 id 字段就直接用；否则用抓取顺序生成 `R001`、`R002`……**并在店铺 README 里注明这是"抓取序号，非平台原生ID"**，避免被误当真实评论ID使用。
- **评论型号 + 对应链接**：这是历史上最难拿准的字段——一个买家的一次订单可能对应多个型号行，多个型号行有时共用同一段评论文字；评论区里还可能夹杂供应商客服的回复（不是买家评论）。判断是不是客服回复：通常没有对应的星级评分，或者署名是店铺员工姓名而非买家名——这类行要过滤掉，不计入评论记录。同一条评论文字对应多个型号时，按"型号"拆成多条记录（允许 `review_content` 重复），因为每条记录必须带一个型号+一个链接。
- **评论时间**：不同店铺展示精度不一样，尽量转绝对日期，转不了就保留原文本。
- **买家名称**：很多店铺出于隐私只展示部分打码或完全不展示，如实标注 `[未展示]`，不要编。
- **长评论被平台截断**（2026-09-13发现，见 Youro/Sri Lanka+Vietnam 几条评论）：部分评论正文在DOM里就已经被截断在约280字符处，以"..."结尾（大概率是原页面"show more"展开交互没有触发导致抓到的是折叠态文本）。抓取时如果 `review_content` 以"..."结尾，视为疑似截断，理想情况下应该尝试找到并点击展开按钮拿完整文本；实在拿不到完整版就如实保留截断文本（不要为了"完整"而editorial地补写结尾），但**这类截断文本不能用于独立站 `ALL_REVIEWS` 池子**（见下方同步流程的筛选条件），只能留在店铺自己的 `reviews.json`/`reviews.md` 里存档。

## 同步进独立站 ALL_REVIEWS 池子（2026-09-13起固定流程）

每次抓完一个店铺（不限于福唯自家店铺，**竞品店铺也要同步**——这是2026-09-13经用户明确确认的决定，见下方"⚠️ 一个业务风险，已告知用户并按用户决定执行"）之后，把新数据合并进 `fouwell-website/js/review-pool.js` 的 `ALL_REVIEWS`，全量重新生成（不是追加），流程：

1. **合并候选池**：读取 `wiki/marketing/_alibaba-reviews/*/reviews.json`（全部店铺，不只是新抓的那个——因为要重新算每个国家的Top2，新店铺可能挤掉旧店铺原本入选的某条），按 `(review_content.strip().lower(), buyer_country)` 去重（同一订单多个型号常common同一段评论文字，只算一次）
2. **筛选条件**：
   - `overall_stars >= 4`
   - `review_content` 非空
   - **只保留英文**（独立站是英文站；非英文的真实评论留在店铺自己的 `reviews.json`/`reviews.md` 里，不翻译、不硬凑进池子）
   - **排除渲染不完整的截断文本**——已知有的店铺页面把长评论截断在约280字符处以"..."结尾（原始DOM里的"show more"没被展开，是已知的抓取局限，见下方"已知局限"新增一条），这类文本半句话卡住展示出去不专业，直接排除，不要因为想凑数就展示不完整的引用
   - **排除明显不是真实自然评论的内容**——比如买家把AI生成草稿的原始脚手架文字（"Here's a possible review for...*Title:*..."）整段粘贴当评论提交，这种要人工识别排除，不属于语言/星级过滤能自动拦住的情况，抓取/合并时留意
3. **按国家封顶**：每个国家最多2条，避免大批量订单的某个国家刷屏。国家候选超过2条时，优先选内容更具体/更有信息量的（提到具体型号、具体场景、具体客服姓名等），不是随手挑最先出现的两条
4. **文本清洗**（不改变原意，只处理展示格式）：把店铺用的全角"："统一转成半角":"；去掉文本末尾多余的引号等排版残留字符；把内嵌换行合并成空格
5. **写回 `js/review-pool.js`**：每条记录格式 `{ rating: N, country: '...', text: '...', source: '<店铺slug>' }`——`source` 字段是维护用的溯源标记（哪条数据来自哪个店铺的`reviews.json`），**不参与任何展示逻辑**，纯粹方便以后追溯/审计
6. **`SELLER_AGGREGATE_RATING` 不在这次同步范围内**——这个字段只代表福唯自己作为Offer.seller的真实评分，只能用 `fouwell` 店铺自己的数据更新（用页面自带的概览统计数字，不是翻页重新点数出来的数字——原因见 `fouwell/README.md`"已知局限"关于两者对不上的记录），不能被其他店铺的数据污染
7. 跑一遍语法/逻辑校验：`node -e` 起一个 vm sandbox 加载 `review-pool.js`，确认 `pickProductReviews`/`buildProductAggregateRating` 能正常跑且结果确定性不变
8. **重新生成静态产品页**：`cd fouwell-website && node scripts/build-product-pages.js`——review-pool.js 改了但不跑这一步，48个静态预渲染页面里嵌的评论卡片和JSON-LD还是旧数据，跟JS水合后的新数据不一致
9. `fouwell-website` 是独立的git仓库（嵌套在wiki仓库目录下），改动记得提醒用户是否要单独commit/部署，不要越权替用户操作git

### ⚠️ 一个业务风险，已告知用户并按用户决定执行

独立站上每条 `ALL_REVIEWS` 展示的评论卡片都标注"Verified Buyer"，JSON-LD `Review.author` 也写 "Verified Buyer (国家)"。当池子混入竞品店铺（非`fouwell`）的数据后，这个标注对那些条目而言不是字面真实的——那是"某个阿里卖家的真实买家"，不是"福唯自己的买家"。这类嫁接评论存在被认定为虚假评论的风险（多数电商平台政策和部分地区消费者保护法规明确禁止）。**这个风险已经在2026-09-13向用户完整说明，用户选择"所有已抓取店铺都同步"这个方案，明确知情后决定**——按此执行，不需要每次同步时重复确认，但如果规则将来又变了，要回来更新这一节和 `review-pool.js` 头部注释。
