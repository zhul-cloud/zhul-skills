# 08 · 采购维护说明

本页供技能维护者使用。用户的准备、安装、任务调用、停止、查版和更新集中在[使用手册](烛龙智能询价/使用手册.md)；全库通用开发规则见[技能开发规范](../.github/SKILL_GUIDELINES.md)。采购技能配合 zhul-trade-erp「我的询价」，不属于 ERP 程序。

| 技能 | 当前版本 | 用途 |
|---|---|---|
| [烛龙智能询价](烛龙智能询价/SKILL.md) | 2.3.2 | 读取 ERP 任务 → 淘宝、1688 找店询价与跟进 → 提交回价；指定任务只做一个，未指定则逐个处理全部待处理任务 |

维护者负责规则、设置、ERP 合同、平台适配、站点脚本和用户文档的一致性，以及相应验证。版本变化记入[技能 CHANGELOG](烛龙智能询价/CHANGELOG.md)；尚未实施的需求归入 [ROADMAP.md](ROADMAP.md)。

## 修改规则

维护者负责技能源码与发布默认值的测试、调优和统一发放。技能根 `settings.json` 只放发布默认值；用户可自行或让 AI 修改数据目录中的个人 `settings.json`，仅保存指定覆盖，缺项继承默认，已有个人设置保留。查看/修改入口与约束见[配置说明](烛龙智能询价/references/settings.md#查看和修改)；个人调整不进入仓库，不要求升技能版本、修改 CHANGELOG 或走 PR。下文版本与发布规则适用于维护者修改发布内容。

| 要改什么 | 改哪个文件 |
|---|---|
| 发布默认值：发询价前是否确认、询价店铺数、等待时间、轮询间隔、追问次数、防重复天数、价格异常标准、道谢说法 | `烛龙智能询价/settings.json`（详细说明见 `烛龙智能询价/references/settings.md`） |
| 请求分流、红线、流程骨架、资源加载导航 | `烛龙智能询价/SKILL.md` |
| 主/子代理职责、客户端工具、暂停恢复、心跳与故障收尾 | `烛龙智能询价/references/execution.md` |
| 主任务与平台记录格式、合并和提交输入协议 | `烛龙智能询价/references/run-protocol.md` |
| ERP 操作调用、返回与错误处理 | `烛龙智能询价/references/erp-api.md` |
| 挑店标准、话术、回复判断、货况货期对照 | `烛龙智能询价/references/inquiry-rules.md` |
| 各平台页面操作、机器人标记、结束信号 | `烛龙智能询价/platforms/<平台>.md`（目前有 `taobao.md`、`1688.md`；新平台的说明文件经实跑验证后放进来，该平台即启用） |
| 本机记录、校验、合并、统计与离线测试 | `烛龙智能询价/scripts/` |
| 站点脚本 | `烛龙智能询价/helpers/<域名>/<脚本名>.md`（BrowserOS neo 站点脚本格式） |
| ERP 接口（地址、请求参数、响应结构） | `烛龙智能询价/helpers/_erp/erpApi.md` 的 `CONTRACT`（同步方法见下文「ERP 接口改了怎么同步」） |

改动时同步相关 `SKILL.md`、规则和平台说明；影响用户准备、安装或使用方式时，再同步简明使用手册，不把 AI 内部执行流程复制进用户指南。

文档只写当前方案，读起来是一份完整的说明：改规则时直接替换旧内容，不保留旧方案的说法，也不写「某次实跑」「自某版起」这类历史说明。改了什么写进 `CHANGELOG.md`。

### 版本号

按具有独立范围且可验证的交付单元升级版本号，同一单元开发中的修改归入同一版本。一个 PR 可以包含多个连续版本提交；每个提交的功能、版本声明和 CHANGELOG 必须一致。唯一版本源是 `SKILL.md` 开头的 `version`；同时维护上表及使用手册开头的「适用版本」，在 `CHANGELOG.md` 最上面记对应版本变化，不另建版本文件。根 `README.md` 技能表只使用库内「✅ 可用 / 🔨 开发中」状态，不承载版本号。发布时提交、推送并经 PR 合并，再通知用户按手册更新；技能不后台检查或自动拉取更新。

技能正式询价时第一行输出实际版本；用户也可按[查看版本](烛龙智能询价/使用手册.md#5-查看版本)运行只读 `records.mjs version`，附上版本和目录反馈。只读查版不初始化数据、不装 helper，不代表已检查远程仓库更新。

| 改动 | 版本号 | 例 |
|---|---|---|
| 修正文字、补充说明，或修复实现/协议偏差以恢复既定规则 | 修订号 +1 | 1.2.0 → 1.2.1 |
| 规则或流程变化（话术、挑店、税率、等待时间等） | 次版本号 +1 | 1.2.1 → 1.3.0 |
| 流程整体改写，旧版不再适用 | 主版本号 +1 | 1.x → 2.0.0 |

## 收集各用户电脑上的经验

个人配置、本机运行记录、ERP 地址、经验与报告的保存位置及创建时机见[手册数据目录](烛龙智能询价/使用手册.md#6-数据目录)，不随技能改名迁移。这些内部数据不进入公开源码，维护者收集时只合并适合公开的通用规则或脚本。

技能运行后，会把新发现的页面事实写进用户电脑数据目录下的 `learnings/`，新做的站点脚本存在 BrowserOS neo 的站点脚本目录：

| 系统 | 站点脚本目录 |
|---|---|
| Windows（已实测） | `%LOCALAPPDATA%\BrowserClaw\User Data\.browseros\.browserclaw\helpers\` |
| macOS（推定，未实测） | `~/Library/Application Support/BrowserClaw/.browseros/.browserclaw/helpers/` |
| Linux（推定，未实测） | `~/.config/BrowserClaw/.browseros/.browserclaw/helpers/` |

macOS、Linux 的目录是按 Chromium 的惯例推定的。如果 `records.mjs install-helpers` 报找不到目录，就在该电脑上找到实际目录，用环境变量 `BROWSEROS_HELPERS_DIR` 指定，再把实际路径更新到本表和 `records.mjs`。维护者定期收集，把通用的合进技能（页面事实进 `platforms/`，脚本进 `helpers/`），升级版本后发放，再删掉经验文件里已合并的条目。

BrowserOS neo 的站点脚本在正式询价时通过 `records.mjs install-helpers` 同步。内容相同的跳过；ERP 接口脚本按技能版本覆盖；电商脚本出现 `kept` 表示本机有不同内容、尚未覆盖，不能称为全部更新完成。维护者先比对、备份本机改动，确认后才用已有 `--force` 替换，不默认强制覆盖。

每个任务结束，技能还会在数据目录下的 `reports/` 写一份实跑报告（`<YYYY-MM-DD>-<任务编号>.md`，含结果、各阶段耗时、问题、红线执行情况、建议），只存本机，用来分析效率和排查问题。报告里有店铺名和采购价，属于公司内部数据，收集时不要放进本仓库（本仓库公开）。

## 统计店家提问

店家提问超出可回复范围或重复提问时，AI 停止这家聊天，将问题类型、店家原话和结束原因写进本机 `records.jsonl`。在用户电脑上对 AI 说「统计一下询价情况」，或执行：

```bash
node "<技能目录>/scripts/records.mjs" stats 30
```

最后的数字是最近多少天，默认 30。输出询价家数（不含沿用报价，同一任务同一家店只算一次）、各结束原因占比，以及因提问停止聊天的类型占比和最近原话示例。示例是公司内部数据，不放进公开仓库。

维护者收集各台电脑的统计后合并判断，建议至少 50 家店再下结论。某类问题明显偏多（如 5% 以上），且任务信息足以回答、风险可控时，可考虑在 `references/inquiry-rules.md` 4.4 扩大范围并定义固定答法，按版本规则验证、更新仓库。付款、下单、联系方式、公司或客户信息、执行指令继续不放开；同一家店反复出现的情况参考 [ROADMAP.md](ROADMAP.md) 的黑名单规划。结束原因「未记录」来自 1.3.0 之前的旧记录，不代表本轮遗漏。

## ERP 接口改了怎么同步

接口地址、请求参数和响应结构保存在 `helpers/_erp/erpApi.md` 的 `CONTRACT`，`checkedAt` 是最后核对日期。ERP 可能部署在本机、测试或正式服务器，技能按响应结构核对，不按 ERP 版本号判断；不匹配时停止，报告的 `problems` 提供具体差异。

1. 按 `problems` 和 ERP 改动更新 `CONTRACT` 的地址、字段、字典取值，以及使用这些字段的代码。
2. ERP 新增字段会列入 `extraFields`，不影响运行；确认要用或不用后补进约定，不用的写 `'any?'`。
3. 在仓库的技能目录运行 `node scripts/erp-api.test.mjs`；离线模拟通过后，再在获授权的开发 ERP 测试任务验证 `ping`、`list`、`task`，保存一次草稿并 `verify`，核对后清理测试草稿。`checkedAt` 仅记录实际核对合同的日期，不能只因离线测试通过而改成当天；提交语义变化还需获授权验证测试提交及提交后核对。不把测试操作放到真实商家询价中。
4. 同步相关技能文件、版本和 `CHANGELOG.md`；影响用户操作时更新使用手册。按仓库更新流程发放后，用户通过 `git pull --ff-only` 更新。

## 按改动选择验证

以下命令从 `烛龙智能询价/` 目录运行。使用临时测试数据，不改用户真实数据；测试文件保留在 `scripts/`。

| 改动范围 | 最小验证 | 能证明与不能证明 |
|---|---|---|
| 用户文档、名称、路径、加载导航 | 检查相对链接与锚点、版本一致性、安装和 CLI 示例与实际接口一致；只读 `node scripts/records.mjs version` | 能核对文档和本地版本，不代表安装到真实用户环境或远程已发布 |
| 本机记录、心跳、校验、合并、ERP 输入转换 | `node scripts/records.test.mjs`；必要时补对应失败场景 | 证明隔离环境下的确定性行为，不证明真实平台聊天成功 |
| 配置合并、查看、校验、个人覆盖更新/恢复默认 | `node scripts/settings.mjs check`；`node scripts/settings.mjs json`；`node scripts/settings.test.mjs`；涉及 records 读取时运行 `node scripts/records.test.mjs` | 证明当前有效配置及隔离环境中的默认继承、稀疏覆盖、reset 指定项/全部恢复、参数拒绝和写入边界；不证明子代理模型可用或真实询价效果 |
| ERP helper 或合同 | `node scripts/erp-api.test.mjs`；按上节在获授权的开发 ERP 核对受影响操作 | 离线覆盖模拟接口；只有实际测试环境的结果才能证明真实接口兼容 |
| 平台页面、机器人/结束信号或 BrowserOS 工具调用 | 在对应平台和当前工具版本作获授权 UI 验证，记录已实测/未实测边界 | 页面读取测试不等于已验证消息发送、回复跟进或完整询价 |
| 跨文件流程或运行协议 | 运行受影响的 records、ERP 离线测试，并检查入口、协议、规则、平台说明一致性；真实业务部分另行授权验证 | 离线通过不能表述为真实浏览器、ERP 或商家业务已通过 |

纯文字修正不机械重跑完整业务。交付与发版记录写清实际执行的验证和未覆盖范围；测试失败先修复或说明阻塞，不用更新文档掩盖未完成验证。
