# 执行与协作

主代理仅在需要并行调度、暂停恢复或异常收尾时读对应章节；平台代理读共享协作约束、派发任务和自身客户端章节。单代理只需本文「单代理交替推进」「收尾」「停止或继续」。

`subagents.enabled` 为 `true`、本次启用两个及以上平台、且所用的 AI 支持子代理时，用**子代理并行**；否则用**单代理交替推进**。

### 子代理并行

每个启用平台派一个子代理，各平台同时挑店、询价、跟进。

| 角色 | 负责 |
|---|---|
| 主代理（用户开会话的 AI） | 准备、[ERP 任务读取与填报](erp-api.md)、[本地防重复与记录](run-protocol.md)、派发子代理、转告用户、合并结果、收尾汇报及取下一个任务 |
| 平台子代理 | 只负责自己的平台：[挑店、发询价与跟进](inquiry-rules.md#8-执行挑店与会话)，结果写进本次目录的 `run-<平台>.json` |

## 共享协作约束与派发

**派发**：模型和思考深度按 `subagents` 里所用 AI 的配置（Claude Code 用 `subagents.claude`，Codex 用 `subagents.codex`；留空的项沿用默认）。给每个子代理的任务说明要写清：

- 平台名称，以及它要读的文件：[SKILL.md「关键红线」](../SKILL.md#关键红线)、[inquiry-rules.md](inquiry-rules.md)、[run-protocol.md「run.json」](run-protocol.md#runjson)及「平台记录与合并」、准备时通过 settings.mjs json 读取的有效配置合并值（直接传完整值，不让子代理用原始默认文件替代）、需要解释时再读 [settings.md](settings.md)、`platforms/<平台>.md`，本机经验文件 `<数据目录>/learnings/<平台>.md`；
- 本任务每个型号的 `itemId`、型号、数量和单位、系统话术、该平台的全部货源直达链接（`run.json` 里 `items[].links` 的该平台部分，按顺序），以及报价截止时刻 `deadline`。子代理写报价时 `itemId` 必须用这里给的值；
- 按 [run-protocol.md「本地防重复」](run-protocol.md#本地防重复)查到的该平台结果（哪些店沿用、哪些店不再问），沿用报价也写入平台文件，因为合并时会按平台覆盖；
- 本次目录路径和要写的文件 `run-<平台>.json`；
- `confirmBeforeSend` 的值；
- 浏览器约束：用 `name_session` 把会话命名为「inquiry <任务编号> taobao」或「inquiry <任务编号> 1688」（名称要含英文字母或数字），只在自己新开的标签页里操作，不动 ERP 页面、其他平台和用户的标签页；结束时关掉自己打开的标签页。
- 打卡和自检：挑店时每打开一条链接、每确认一家店，发询价和跟进时每一轮（查看一遍回复、发出一家），都执行 `node "<技能目录>/scripts/records.mjs" beat "<本次目录>" <平台> <在做什么>`（如「挑店 第 2 条链接」「等回复 3 家」）；停下等人处理时加 `--paused`。超过 `subagents.stallMinutes` 分钟没打卡，主代理会按卡住处理。所有店都结束、写好 `stages.repliesDone` 后，执行 `records.mjs check "<本次目录>" <平台>` 自检平台文件，有问题改好再结束。

**子代理不做的事**：不打开、不修改 ERP；不写 `run.json`、不执行 `records.mjs finish`；不直接问用户。

**浏览器**：各执行者按 [SKILL.md「准备」](../SKILL.md#准备)读取当前 BrowserOS 使用说明；然后先列出现有标签，再复用窗口。多个代理连接 BrowserOS neo 时可能共享会话或标签组，不同的 `name_session` 名称不等于互相隔离；各代理记下自己打开的标签 ID 和网址，只操作分配给自己的平台和标签。共享登录需要用户处理时，暂停所有受影响的操作，不受影响的平台继续。

- BrowserOS 返回的会话句柄（`session`）可能在头几次调用后变化，之后的调用一律传最近一次结果里给出的句柄。
- 点「客服」打开的聊天页显示为用户的标签页，BrowserOS 不会在这类页面上自动加载站点脚本，要按平台说明「聊天页上的脚本要手动加载」调用。
- 这些显示为用户标签的聊天页和重复标签都是本次询价打开的，结束时照样关闭；关闭时报「No tab with given id」的，说明已经随同组标签关掉了，忽略即可，最后列一次标签确认没有残留。

## 暂停与恢复

**需要人处理时**：子代理遇到登录失效、验证码或滑块、账号异常、需要选择的账号设置，或 `confirmBeforeSend` 为 `true` 需要用户确认店铺和话术时：

1. 子代理停下，把当前进度写进 `run-<平台>.json`（每家店的状态、发送和回复时间），打一次带 `--paused` 的卡，返回：需要处理什么、在哪个标签页、处理后接着做什么。
2. 主代理转告用户，其他平台的子代理照常进行。`confirmBeforeSend` 为 `true` 时，等待所有未跳过平台挑店完成，汇总店铺和话术，一次请用户确认；明确同意前任何平台都不发询价。其他需要人处理的情况及时转告，能合并的合并说明。
3. 用户处理好后，主代理先执行一次不带 `--paused` 的 `beat`（如「恢复询价」），清除暂停状态，再让同一个子代理接着做（用能延续它上下文的方式）；无法延续时，确认原执行停止后重新派发一个子代理，从 `run-<平台>.json` 的进度接着做。
4. 暂停期间，已发出询价的店照常计时；恢复后先处理这期间的回复。是否超时按店家消息上显示的时间判断（见 [inquiry-rules.md「每家店的进展」](inquiry-rules.md#每家店的进展)），不按读到消息的时间。

## 打卡与监控

**盯进度**：派发时，主代理给每个平台先打一次卡（`records.mjs beat "<本次目录>" <平台> 已派发`），然后用 `node "<技能目录>/scripts/records.mjs" watch "<本次目录>"` 盯各平台的打卡。`watch` 是本机的一个小程序，不消耗 AI 用量：后台持续运行时每 15 秒看一次，某个平台超过 `subagents.stallMinutes` 分钟没打卡（停下等人处理的不算），或所有平台都结束时退出，输出 `result`（`stalled` 卡住、`finished` 本地记录声明全部结束，仍须 check/merge 核验）和每个平台最后一次打卡在做什么。`watch --once` 只检查当时的状态；发现卡住的实际延迟还取决于客户端唤醒和工具调用，不能保证固定时限。仅按本次客户端读取「Claude Code 派发与续跑」或「Codex 派发与续跑」。

## 子代理卡住时

**处理**（`watch` 输出 `stalled`）：

1. 停掉这个子代理（Claude Code 用 TaskStop，Codex 用 `interrupt_agent`），确认已经停了。不重新派发：重派要重新打开聊天页、核对已发的内容，花的时间比剩下的等待还长，也容易重复发消息。
2. 读这个平台的 `run-<平台>.json`：已结束的店照原样；没结束的店按已有信息结束，有人工回复的记「已回复」，只有机器人回复的记「自动回复」，没回复的记「未回复」，结束原因都记「子代理卡住」。这个平台不再发任何消息。把因此未完成的型号写进平台文件的 `incompleteItems`（每条 `{ itemId, reason: "子代理卡住" }`）；不能确认影响范围时，列出本平台负责的全部型号。还没写平台文件的（如挑店时就卡住了），写一个空 `shops`、带 `skipped` 和 `incompleteItems` 的平台文件。
3. 其他平台照常进行，全部结束后合并，进入 [ERP 填报](erp-api.md#草稿核对提交一次与再核对)。`incompleteItems` 里的型号有正常报价就照常提交；所有平台都没有价格时，不标无货、不提交这个型号，任务标记为需人工处理（见 [erp-api.md「ERP 错误与重试边界」](erp-api.md#erp-错误与重试边界)，原因写明哪个平台卡住）。
4. 汇报和实跑报告里写明哪个平台卡住、最后一次打卡在做什么、几家店因此提前结束。

## 合并与记录失败

**结束**：所有平台正常完成或已按故障规则收尾后（`watch` 输出 `finished`，或已确认各平台本轮执行停止且记录已收尾；等人处理的暂停不算完成），主代理执行 `node "<技能目录>/scripts/records.mjs" merge "<本次目录>"`，把各平台的 `run-<平台>.json` 合并进 `run.json`，再进入 [ERP 填报](erp-api.md#草稿核对提交一次与再核对)。`merge` 报错时：

- 格式问题（字段名写错、`status` 写法不对、缺店铺名等）：主代理在平台文件里改正，不改报价内容（价格、含税、货况、货期、店家原话），再合并。
- 平台文件缺失、读不出来，或内容对不上（如报价的型号 ID 不在任务里、看不出是哪个型号）：让同一个子代理只重写记录一次（Claude Code 用 SendMessage，Codex 用 `followup_task`），不恢复询价、不再发消息；已按卡住规则停止的平台不唤醒，直接按下一条收尾。
- 重写后仍不行：把这个平台的文件改写成空 `shops`、带 `skipped`（写明原因）和 `incompleteItems`（本平台负责的型号及记录损坏原因）再合并，其他平台照常填报；不凭聊天记录或印象补价格。因此没有任何价格的型号不标无货，按上面「子代理卡住时」第 3 条处理。用户主动跳过平台不填 `incompleteItems`，不能靠 `skipped` 的文字推断。汇报里写明这个平台的结果没有录入，能看出问过哪些店的一并列出（这些店没写进询价记录，防重复认不出它们）。

### Claude Code 派发与续跑

- 用 Agent 工具派发，每个平台一个，`subagent_type` 用通用代理（`general-purpose`）。非空的 `subagents.claude.model` 传入 `model`，非空的 `subagents.claude.effort` 传入 `effort`；空字符串不传，沿用默认。让子代理在后台运行，各平台同时进行。
- `prompt` 里写全上文要求的文件绝对路径、任务信息、当前设置和已获授权的范围。子代理看不到主代理的聊天，不能依赖它知道上下文。子代理不再向下派发子代理。
- 记下每个子代理的 ID 和名称与平台的对应关系。子代理在后台运行时，结束或停下都会通知主代理。派发后用 Bash 的后台运行方式执行 `watch`，它退出时也会唤醒主代理；主代理不反复查看进度。被子代理的通知唤醒时 `watch` 还在运行，就不用管它；`watch` 已经退出、还有平台在进行时（如处理完卡住的平台、用户处理好暂停的平台后），再启动一次。
- 子代理需要人处理时，把进度写进 `run-<平台>.json`，以报告结束本轮：需要处理什么、在哪个标签页、处理后接着做什么。用户处理好后，主代理用 SendMessage 发给同一个子代理，让它带着原来的上下文接着做。
- 重新派发或改用单代理前，先确认旧子代理已经结束，还在运行的用 TaskStop 停止并核实。同一平台只能有一个执行者。续跑前读取最新的平台文件，并核对聊天里已经发出的内容，保留发送时间、追问次数和道谢记录，避免重复发送。
- 工具名和参数以当前客户端的实际工具声明为准。指定的模型或思考深度不可用、子代理拿不到 BrowserOS neo 的工具或必要文件时，停止已启动的平台子代理并核实，改用单代理交替推进，说明原因和实际使用的模型。

### Codex 派发与续跑

- 派发前查看当前会话的子代理工具及其参数、可用模型和深度。`settings.json` 是本技能的输入，不是 Codex 的原生配置文件；不要为它修改用户电脑上的全局 `config.toml`。
- 使用 `collaboration.spawn_agent` 时，非空的 `subagents.codex.model` 传入 `model`，非空的 `subagents.codex.effort` 传入 `reasoning_effort`；空字符串不传。显式设置任一项时用 `fork_turns="none"`，把上文要求的文件绝对路径、任务信息、当前设置及已获授权的范围完整写进 `message`，不能依赖子代理继承聊天。`task_name` 包含任务编号、平台和派发轮次，避免与仍存在的代理重名；不再向下派发子代理。
- 记录返回的代理 ID 与平台对应关系。`list_agents` 查看状态，`wait_agent` 等待任意代理的消息或状态变化，每次最多等 60 秒；该工具不接受某个代理句柄作为等待目标，返回的摘要不能代替读取实际消息和平台记录。每次被唤醒或超时，都执行一次 `watch "<本次目录>" --once`，按最后一次实际打卡时间判断，输出 `stalled` 时按「子代理卡住时」处理，否则接着等；不能只在超时时检查，也不能因别的平台有消息而重新计算卡住时间。等待超时本身只表示尚未返回，不代表失败。子代理用 `send_message` 向主代理报告需要处理的情况，落盘后结束当前轮次等待；`send_message` 只投递消息，不触发空闲代理执行，用户处理完成后先清除暂停打卡，再用 `followup_task` 让原代理接着做。
- 重新派发或改用单代理前，先确认旧代理已结束当前执行，必要时用 `interrupt_agent` 中断并用 `list_agents` 核实状态；中断不销毁代理，也不意味着并发容量已释放，派发下个任务前按实际状态和容量检查。同一平台只能有一个执行者。读取最新平台文件并核对聊天中已经发出的内容再续跑，保留发送时间、追问次数和道谢记录，避免中断后重复发送。
- 当前客户端若提供其他工具名，以实际工具声明中的派发、等待、停止、续跑能力为准，不调用不存在的接口。指定模型或深度不可用、工具不支持设置它们、并发名额不足，或子代理无法访问必要文件及 BrowserOS neo 时，停止已启动的平台代理并核实状态，改用主代理单代理交替推进，说明原因与实际使用的模型；不能确认旧代理已停止时，暂停受影响平台，不重复接管。

### 单代理交替推进

主代理自己完成全部步骤。[挑店与会话](inquiry-rules.md#8-执行挑店与会话)在各启用平台交替进行：`confirmBeforeSend` 为 `false` 时，**哪个平台先挑完本任务所有型号的店，就先开始给它发询价**，同时继续挑其他平台的店；为 `true` 时，先汇总所有未跳过平台的店铺和话术，得到一次明确确认后再发送。之后每一轮轮流查看各平台的聊天页。

## 收尾

1. 关闭这个任务在各平台打开的标签页（商品页、搜索页、聊天页，包括点击打开、显示为用户标签的页面），保留用户和其他任务原有的标签。自己的 ERP 标签页留着给下一个任务用，全部结束时再关。
2. 按 [run-protocol.md「任务汇报」](run-protocol.md#任务汇报)向用户汇报，并按该文件「实跑报告」写报告；发现新的页面情况按该文件「本机经验」记录。

## 停止或继续

1. 用户指定了任务编号时，这个任务结束就进入本节总汇报，不取下一个。没指定时，这个任务结束（提交成功，或因第 3 条里可以继续的原因转了人工）、已执行 `finish`、已汇报并写好实跑报告后才继续。
2. 取下一个：`erpApi` 的 `{ op: "list", done: false }`，再用 `records.mjs next` 按列表顺序取第一个本机没提交过回价、没跳过、也没标记为需人工处理的任务。上一个任务是按 [erp-api.md「选任务与读取」](erp-api.md#选任务与读取)跳过的（询盘已取消、已回过价）也照样取下一个。有就回到 [erp-api.md「选任务与读取」](erp-api.md#选任务与读取)的新建本次目录步骤开始做，`name_session` 改成新的任务编号；用子代理时，确认上一个任务的平台执行均已停止，再按当前工具和并发容量派发，Codex 使用新的 `task_name`。`next` 为 `null` 时进入本节总汇报。
3. **出了问题，按原因决定停下还是继续**：
   - 接着做下一个：只和这个任务有关、已标记为需人工处理的，即 ERP 拒绝了内容（`ERP_BIZ`、`SKILL_INPUT` 改两次仍失败）、核对有差异、某个平台卡住或记录损坏，或报价截止时未完成挑店/发送导致有型号没价格。
   - 停下，不再取下一个任务：`ERP_HTTP` 重试后仍失败（多半是网络或 ERP 服务器的问题，做下一个也会提交失败，白白问了店家），这个任务照样标记为需人工处理；`erpApi` 返回 `ERP_CONTRACT`；用户说停。
   - 用户说停时，立即停止当前询价和所有平台代理（Claude Code 用 TaskStop，Codex 用 `interrupt_agent`），确认各执行者已停止后，才读取已落盘进度、合并能校验的记录并执行 `finish`、写报告和汇报；不再发商家消息、不再调用 ERP 写入。已实际询问但尚未结束的店，按已有回复设置 `status`，`endReason` 记「用户停止」；未发送的候选店不补造询价或发送时间。没有进入询价或建立记录的任务不补造询价记录。用户停止与等人处理的暂停不同，不自动续跑。
   - 只有人能处理的情况（没登录、验证码、账号设置）是暂停：等用户处理好，接着做同一个任务，完成后照常继续。
4. **总汇报**（全部结束或停下时）：

   ```
   本次共完成 N 个任务：IQ0001（3 个型号，8 条报价）、IQ0002（2 个型号，1 个无货）……
   跳过：IQ0004（询盘已取消）
   需人工处理：IQ0003（<原因>，<实际保存/提交状态及未完成范围>）
   结束原因：本轮已无可自动处理的待处理任务  /  停在 IQ0003：<原因>
   ```

   然后关闭自己的 ERP 标签页。
5. 连续做多个任务时，对话可能变长、被压缩：每个任务开始时从接口和本次目录的 `run.json` 重新读状态，不依赖之前的记忆。

## 故障速查

| 情况 | 处理 |
|---|---|
| BrowserOS neo 连不上 | 停下，请用户启动 BrowserOS neo 并检查 MCP 连接 |
| 没登录、验证码、账号异常 | 暂停出问题的平台（ERP 出问题则整体暂停），请用户处理；不能记成「无货」 |
| `erpApi` 返回 `ERP_CONTRACT` | 立即停止任务，提示用户「ERP 接口已修改，烛龙智能询价没有同步，请更新技能」，把 `problems` 写进汇报和实跑报告（见 [erp-api.md「ERP 错误与重试边界」](erp-api.md#erp-错误与重试边界)） |
| `erpApi` 调用不到 | 确认已执行 `install-helpers`、`config.json` 的 ERP 地址与 ERP 标签页一致，且本次 `run` 开始前已打开自己的 ERP 标签页 |
| 聊天页「连接断开」 | 只关本次自己打开的同平台多余聊天页，按平台说明重新打开一个；原有页影响连接时请用户处理 |
| 平台弹出需要选择的账号设置（如聊天工具） | 停下，说明选项和影响，请用户决定 |
| 子代理卡住（`watch` 输出 `stalled`） | 按「子代理卡住时」处理：停掉它，没结束的店按已有信息结束，不重派 |
| 合并失败（`merge` 报错） | 按本文「合并与记录失败」处理：格式问题主代理改，文件坏了让原子代理仅重写记录一次，仍不行按该节记 skipped 和 incompleteItems |
| 子代理报错返回、中途出错 | 先查代理状态；等待超时不等于失败。确认原代理停止后，读取 `run-<平台>.json` 并核对已发送消息，再恢复原代理或重派；无法确认停止则暂停该平台，仍失败时按已有记录结束并说明 |
| 所用的 AI 派发子代理失败 | 先停止并核实已启动的平台代理，读取已有进度后改用单代理交替推进，在汇报里说明；无法确认停止的平台不重复接管 |
| 站点脚本调用不到 | 先打开该域名的页面，下一次 `run` 才能调用；仍不行就按该平台说明里的手动步骤操作 |
| 提交回价失败 | 按 [erp-api.md「ERP 错误与重试边界」](erp-api.md#erp-错误与重试边界)处理：能改正的改正后重试，同一错误最多改两次；解决不了就标记为需人工处理，按实际保存/提交阶段汇报，不重复提交 |
| 型号已报给客户（只读） | 跳过该型号，汇报里说明 |
