# 执行与协作

主代理需要补充信息或业务选择时读「主代理提问与续跑」，需要并行调度、浏览器暂停恢复或异常收尾时读对应章节；平台代理读共享协作约束、派发任务和自身客户端章节。单代理也遵守相应提问与暂停边界。

`subagents.enabled` 为 `true`、本次启用两个及以上平台、且所用的 AI 支持子代理时，用**子代理并行**；否则用**单代理交替推进**。

### 子代理并行

每个启用平台派一个子代理，各平台同时挑店、询价、跟进。

| 角色 | 负责 |
|---|---|
| 主代理（用户开会话的 AI） | 准备、[ERP 任务读取与填报](erp-api.md)、[本地防重复与记录](run-protocol.md)、派发子代理、转告用户、合并结果、收尾汇报及取下一个任务 |
| 平台子代理 | 只负责自己的平台：[挑店、发询价与跟进](inquiry-rules.md#8-执行挑店与会话)，结果写进本次目录的 `run-<平台>.json` |

## 共享协作约束与派发

**派发**：模型和思考深度按 `subagents` 里所用 AI 的配置（Claude Code 用 `subagents.claude`，Codex 用 `subagents.codex`；留空的项沿用默认）。给每个子代理的任务说明要写清：

- 平台名称，以及它要读的文件：[SKILL.md「关键红线」](../SKILL.md#关键红线)、[browseros-setup.md「按域注册与核验 helper」](browseros-setup.md#按域注册与核验-helper)、[inquiry-rules.md](inquiry-rules.md)、[run-protocol.md](run-protocol.md)的「受控保存与事件」「每日时间线与关键事件」「run.json」「平台记录与合并」、准备阶段通过 `settings.mjs json` 读取的本次 `settings` 合并值（直接传完整有效值，不传原始默认文件让子代理自行当作当前值）、需要解释时再读 [settings.md](settings.md)、`platforms/<平台>.md`，本机经验文件 `<数据目录>/learnings/<平台>.md`；
- 本任务每个型号的 `itemId`、型号、数量和单位、系统话术、该平台的全部货源直达链接（`run.json` 里 `items[].links` 的该平台部分，按顺序），以及报价截止时刻 `deadline`。子代理写报价时 `itemId` 必须用这里给的值；
- 按 [run-protocol.md「本地防重复」](run-protocol.md#本地防重复)查到的该平台结果（哪些店沿用、哪些店不再问），沿用报价也写入平台文件，因为合并时会按平台覆盖；
- 本次目录路径、`runId` 和唯一负责的平台 scope，最新 `run-<平台>.json` 断点及 revision、平台 `status`、未决 `pendingMessage` 和人助请求；按[受控保存](run-protocol.md#受控保存与事件)用 `checkpoint` 保存，不直接覆盖平台 JSON；`completed` 平台不再派发询价，只由主代理补做 ERP 写回；
- `confirmBeforeSend` 的值；
- 浏览器约束：用 `name_session` 把会话命名为「inquiry <任务编号> taobao」或「inquiry <任务编号> 1688」（名称要含英文字母或数字），只在自己新开的标签页里操作，不动 ERP 页面、其他平台和用户的标签页；归属与收尾按[共享浏览器](#共享浏览器)规则。
- 打卡和自检：挑店时每打开一条链接、每确认一家店，发询价和跟进时每一轮（查看一遍回复、发出一家），都执行 `node "<技能目录>/scripts/records.mjs" beat "<本次目录>" <平台> <在做什么>`（如「挑店 第 2 条链接」「等回复 3 家」）；停下等人处理时加 `--paused`。超过 `subagents.stallMinutes` 分钟没打卡，主代理会按卡住处理。关键动作先持久化，发送前记 `pendingMessage`，读回确认后再更新发送事实。所有店真正结束时写 `status: "completed"` 和 `stages.repliesDone`，执行 `records.mjs check "<本次目录>" <平台>` 自检，立即请求主代理代存草稿后再结束。中断时用 `check "<本次目录>" <平台> --partial` 核验断点，不能补造完成时间。

**子代理不做的事**：不启动浏览器、不负责全局连接恢复、不打开或修改 ERP；不写 `run.json`、不执行 `records.mjs finish`；不直接向聊天中的用户提问，业务确认交主代理汇总。连接故障上报主代理，其他浏览器技术阻塞按下文「暂停与恢复」调用 BrowserOS 人助工具，并向主代理上报。

派发、停止、暂停、续跑和平台完成通知，按[时间线事件](run-protocol.md#每日时间线与关键事件)分别记录信号已发出、已收到、已实际执行。发送者保存 sent，接收者收到才保存 received，执行者实际完成对应状态保存后才记 applied；工具已投递、代理空闲或心跳改变都不能代替后两项。无法取得某一步证据时保留未确认，主代理据最新断点和实际执行状态判断。业务/代理信号与操作系统进程信号分开；进程被强杀或断电且没有准确结束时刻时，不补造终止或业务完成时间。

### 共享浏览器

各执行者按 [SKILL.md「准备」](../SKILL.md#准备)读取当前 BrowserOS 使用说明；然后先列出现有标签，再复用窗口。多个代理连接 BrowserOS neo 时可能共享会话或标签组，不同的 `name_session` 名称不等于互相隔离；各代理记下自己打开的标签 ID 和网址，只操作分配给自己的平台和标签。共享登录需要用户处理时，暂停所有受影响的操作，不受影响的平台继续。

- BrowserOS 仅在返回会话句柄（`session`）时，后续调用才传最近的有效句柄；从未返回时不自行构造。工具明确会话 stopped / no longer active 后，不再重复传死句柄，按下节恢复连接和标签归属。
- 点「客服」打开的本任务聊天页可能显示为用户页，先核实来源/归属；helper 按[域注册及加载边界](browseros-setup.md#按域注册与核验-helper)处理，不操作无关用户页。
- 仅清理有本轮创建记录且已确认归属的任务标签；不能只凭重复 URL 或显示为用户标签推断归属。SDK `run` 内的页面句柄和顶层 `tabs` 句柄不可混用，也不能按数字相同推断同页。关闭前在将执行关闭的同一 API 层重新列页，核同层当前句柄、URL、创建记录和 owned 归属；工具提供物理标签标识时再交叉核对，不为取物理标识混用另一层编号。跨 API 映射不可靠时绝不混用，无法核实归属就保留。工具发出用户页或归属警告时立即停止该清理操作，不能继续批量关闭；权限或自动审批拒绝时保留并报告，不换工具或路径强关。导航或关闭后重新列页确认实际状态；`No tab with given id` 只表示当前句柄不可用，不能据此断言该页已关闭。保留用户和其他任务标签。
- 已核实的少量目标可在同一次 `run` 中依次 `await` 只读 helper，每家保留身份与结果；每项按[逐项检查](#访问限制与逐项检查)的实际分类决定能否继续下一项，不无条件循环导航、不并行切换同一聊天页。挑店时达到本条家数即停，30 秒只是整次工具调用预算，不能代替业务暂停或停止边界。ERP 仍按 [ERP 调用协议](erp-api.md#调用接口)每次 `run` 一个操作。此方式不扩展为商家发送批处理。
- 会话复用按[当前账号身份映射](identity-mapping.md)：每个平台在当前具名买家账号范围内查询和现场验证，账号或接收者不符停止复用，不按同名悄然换绑。平台代理将已核实 `identity` 保存到自己平台的 `shops[]`；本地 contacts 写入用 revision 和短锁，冲突先重读合并，不绕锁覆盖。缺独立账号证据时不使用跨运行映射，原断点、未知发送对账和已结束店纪律保持。

## 主代理提问与续跑

本节只处理聊天中的信息补充与业务选择，由主代理统一提问；浏览器页面的登录、凭据、验证、账号设置及接管按下节 [暂停与恢复](#暂停与恢复)处理，普通滑块仅可依该节先尝试一次。已知信息和已获授权不重复询问；店家超出可回复范围的问题仍按[业务规则](inquiry-rules.md#44-答复店家的提问)结束该店聊天，不转成请用户代答后继续。

### 选择当前客户端的输入能力

先检查当前运行时实际工具及限制，不按产品名假定工具存在：

| 当前能力 | 提问方式 |
|---|---|
| Codex 提供 `functions.request_user_input_async` | 使用原生输入/选择框；自由文本问题可省略 `options`，有限选择才给明确选项。调用返回只表示问题已挂起，实际答复异步送达，不当成已回答 |
| 仅有 `request_user_input` | 只在当前已处于 Plan 且实际提供该工具时使用，遵守其选项参数；不切模式绕过限制 |
| Claude Code 提供 `AskUserQuestion` | 按实际工具定义给出选择项；用户也可用自定义文本回答，不强迫 ERP 地址等自由输入选某个预置值 |
| 普通 ChatGPT 或其他运行时、上述工具不可用 | 在聊天中直接提出具体问题，保留原请求和暂停点，等待用户下一条消息；不冒用其他运行时的工具 |

不创建桌面窗口、浏览器弹窗、临时网页或输入脚本来模拟原生输入框。`settings.mjs`、`records.mjs` 只承担既有的确定性校验与保存，不承担聊天等待。

### 何时提问，答后回到哪里

| 原请求与缺项 | 问题与答后动作 |
|---|---|
| 正式询价准备缺 ERP 地址 | 请用户输入实际 ERP 域名或 IP（可带端口，无需协议）；也可粘贴完整地址。按[地址规范化规则](browseros-setup.md#erp-登录)执行 `records.mjs init --erp <地址>`，保存入口 origin；缺协议默认 HTTP，完整地址保留 HTTP(S)。成功后回到原指定 IQ 或原批量请求的准备，不另起任务 |
| ERP 地址无效（新输入或已有配置） | 说明具体主机、端口或输入格式错误，请用户更正并明确保存；不把缺协议当错误，不猜补地址或端口。校验失败保持该暂停点，再问更正，不进入浏览器准备 |
| 仅请求修改 ERP 地址但未给值 | 询问新地址；先按入口要求确认运行中的执行者已停，再校验保存。保存成功即结束该配置请求，不顺带询价 |
| settings 的键、值含糊，或 reset 未指定目标 | 询问具体项/值或「指定项、配置组、全部」范围；按 [settings.md](settings.md#查看和修改)调用既有脚本。无目标不默认 `--all`，配置请求完成后不启动或复活已停止的询价 |
| 准备时配置非法 | 按[准备顺序](../SKILL.md#准备)区分生命周期错误与保留配置错误：坏发布默认值、版本标记或锁错误先停止并报告，不清目录绕过；保留配置非法时报告具体项和可行修复选择，仅用户明确选择具体修复后按配置流程处理，再执行 `settings.mjs json`。尚未进入业务执行的原询价请求，校验通过后继续其准备；若已有询价为修改配置而被停止，则不自动复活。不得把「继续」当成恢复全部默认或任意修复授权 |
| `confirmBeforeSend=true` | 等本 IQ 全部未跳过平台完成挑店，汇总实际店铺、商品链接及各店将发送的完整话术，一次请求确认；不得只确认先完成的平台。明确同意后仅放行该方案，后续按原规则跟进，不逐条再确认。`false` 不增加此确认 |
| 电商 helper 存在未知本机差异 | 先读实际源码并核对差异，说明受影响的域、名称及具体处理范围，提供保留交维护者合并、备份后替换指定 helper、取消受影响动作等可行选择；不提供笼统「全部继续」。按用户明确选择及[注册协议](browseros-setup.md#按域注册与核验-helper)处理并核验，未解决前不调用、不覆盖或另存新版绕过；ERP helper 仍按既有同步规则 |

发送方案遭拒绝或要求修改时，未获同意的消息不发；按明确修改重新整理待确认方案，不能把拒绝当作平台已跳过。仅拒绝而没有后续选择时，保持暂停并问清修改或取消范围；明确取消当前 IQ/请求时按其范围停止执行者、保存可核验进度并收尾，不擅自继续其他 IQ，不伪造 `completed` 或 `skipped`。用户明确只取消某个动作时仅取消该动作，后续若需跳过平台须取得明确选择，仍受既有提交守卫约束。

### 等待与恢复边界

主代理在当前会话保留唯一待答请求及其原请求分支、已知 IQ、暂停点、待答内容/方案和原执行者；可合并必要的相关问题，已明确回答的部分保留，仅补问缺失或无效部分。已有 run 时沿用已有断点，尚无 run 时不虚构目录、IQ 或 BrowserOS 人助状态。依赖答案的动作暂停；异步工具等待时可继续独立工作。未回复、空内容、仅界面预选、关闭输入框均不算同意、完成或失败，不用 `final` 宣告异步待答任务已结束；无工具时用正常文字提问并保留请求等待下一条用户消息。不照搬 BrowserOS 的 20 分钟或连续两次失败规则。

**业务截止在等待期间仍生效**：尚无业务截止的准备/配置问题可直接等待；已有 `deadline` 时，主代理用当前可用的有界等待能力，间隔不超过 60 秒且不越过「截止前 5 分钟」的剩余时间，检查用户停止、任务中断及原截止。到达该时刻即撤销待答发送方案，按既有[截止规则](inquiry-rules.md#每家店的进展)保存进度并收尾，不等答案、不再发送，也不把未询问记为无货；后到的同意不能放行旧方案。收尾仍受平台中断、未决 BrowserOS 人助和 ERP 写入守卫约束，不因业务截止清除它们。

`watch` 不检查截止，`--paused` 也不会产生截止通知，不能只等它退出。有业务截止时，若输入工具会阻塞主代理、无法同时巡检且不能保证截止前返回，则因工具能力限制改为聊天提问，主代理留在本轮以短调用/有界等待巡检，不用 `final` 结束本轮；不能用平台代理仍在运行代替主代理的截止处理。不伪造工具超时参数，不仅为等答案新建执行者或后台定时任务。客户端无法持续等待时保存待答与截止并说明限制，收到回复仍先核截止，不承诺无人值守的准时收尾。

已有任务时，受聊天待答影响的执行者先保存真实业务断点并打 `beat ... --paused`；不把聊天提问写成 BrowserOS `humanHelp` 事件，不以等待伪造 stalled 或 completed。并行发送确认由平台代理保存候选/话术并上报，主代理汇总提问；答复后由主代理按本客户端续跑能力恢复原唯一执行者并清该业务暂停，不新派第二名。BrowserOS 仍有未决请求时不能清其暂停；若原执行者意外停止，先核实旧执行已停再按既有交接恢复。

收到答复先核对是否对应当前待答请求、是否已取消/全局停止，再检查原 `deadline`、最新平台断点、未决发送及 ERP 原写入状态。答案只补齐所问信息/选择；不重置消息计时、不重发未知消息，不以一句「继续」越过 `ERP_CONTRACT`、`ERP_CONFLICT` 或未知提交的只读核对边界。超过截止仍按既有截止规则处理，不能因等答复延长授权。

明确取消按上述作用范围收尾；用户全局「停止询价」「停」优先，停止所有执行者和等待并清除本轮续跑许可，按[停止或继续](#停止或继续)保存与汇报。迟到答复不恢复已取消的请求/动作或已停止的询价，只有用户新一轮明确启动才按原恢复协议核验。主动配置修改请求仍先停止并核实已有执行者，修改完成不自动恢复旧询价，不在运行中热改；尚未进入业务的准备期修复按上表续原准备。

## 暂停与恢复

浏览器页面中的登录失效、账号异常、账号设置及需人工处理的验证等实际阻塞（包括 ERP 登录）使用当前 BrowserOS 的 `request_human_help` / `await_human_help`；风险提示本身不请求人助，必要流程实际受阻、无既有可用路径且无可操作验证时按下节中断，不循环人助。仅下述普通滑块可在人助前尝试一次。ERP 登录表单提交前，AI 先按[ERP 登录](browseros-setup.md#erp-登录)勾选并读回记住我，再交用户处理凭据；交回后 `ping` 核实。聊天信息补充和业务发送确认走[主代理提问与续跑](#主代理提问与续跑)，不能代替技术人助或消耗未决请求。下文请求终态、时限和核验失败次数均指 BrowserOS 人助。

页面加载或身份核验受阻时，同时检查当前页面可见验证区域和可访问的 frame，必要时查看截图。验证码可能呈现为内嵌区域或 iframe；未命中某一种 DOM 结构不能排除验证，不靠重绑或反复刷新绕过。

### 访问限制与逐项检查

每次导航完成后，在等待或读取业务字段前，先核实际 URL、登录状态、可见验证区域及本次目标；每项读取返回后、Hand back 后也重新核验。风险提示文本、`pcResistDetail` / `pcIdentityRisk` 标记仅是风险信号，不单独触发暂停、中断或人助。可在同一正常目标页进行一次只读可用性核验：本步必要商品字段、原型号 SKU、店铺/会话身份可核，登录有效且没有验证码阻塞、读取及发送前就绪检查通过时，继续原挑店、询价、跟进及符合业务条件的草稿/正式提交。非必要图文详情或组件受限不影响上述条件时继续；风险提示不禁止正常业务导航，不要求关联提示页消失；昵称仍在、URL 回到商品域、完整 SKU 或单次 helper 成功也不能代替其余必要检查。

仅在必要步骤实际不可用时按受阻原因处理：已跳登录页则及时暂停后续导航并走登录人助，可操作验证码按原验证流程；目标跳到错误/提示页、必需数据无法读取或聊天无法就绪，先诊断实际受阻范围，单商品缺字段或跳提示页不直接升级为全平台中断，已有可用会话仍按原规则继续。确认平台必要流程受阻、无既有可用路径且无可操作验证可处理时，将该平台记为 `interrupted`，保存实际失败、原因和原断点；保留真实人助终态，原阻塞未恢复仍为 `verified:false`。其他平台按原规则收尾，本轮只留草稿、不正式提交、不取下一 IQ，不误记无货。尚无 run 时结束受阻准备，不虚构平台或业务记录。不得强行绕过、切换账号/指纹，或循环人助、反复刷新、换商品、重启来探测恢复；正常业务仍复用有效页面证据、避免重复访问，达到本条家数即停。

每项异常先分类再决定下一项：登录或可操作验证按原请求暂停恢复；缺 SKU、字段未就绪或单商品读取失败先诊断，不直接等同访问限制。页面可用时优先在当前页补核必要独立型号/规格并保留有效证据，避免离开后为补漏字段复访；相同商品字段可复用，仍按[共同挑店与去重规则](inquiry-rules.md#找店与挑店)逐型号核验，不把登录失效前的页面状态当作恢复后已核验的证明，当前规格和价格须重新核验；已存报价和发送证据仍按原断点保留。未触发实际平台阻塞、暂停、中断或停止时，可保留未确认结果再按原顺序核其他业务候选；读取失败不作错型号、无货或已完成覆盖。

申请前确认目标标签 owned，可用 cockpit 预览及标签元数据交叉检查拟接管页；`selectedTab` 只是预览线索，不保证下一请求的目标，snapshot 或 helper 读取成功也不证明目标已绑定。创建后的实际投递以 `helpRequest.browserTabId` 或实际接管 UI 为准，同时核对提示是否可见；已有人助请求时，修改预览下拉不会更改该请求的目标。请求返回 `waiting` 不等于提示已送达；等待期间的投递核验只读 cockpit、请求返回及已有标签/组元数据，不触碰受阻页、不模拟 Hand back。目标不一致或提示未出现时保留原请求，不盲建第二请求、不连续刷新，也不把 UI 投递失败计为用户处理后的实际核验失败。

用户在主聊天说「已处理」只记录为用户报告，不改原生 `nativeStatus`、不清 `waiting`、不重置请求总时限，也不恢复业务或正式提交；仍由唯一 owner 等原请求，只有 `resolved` 才按下文核验，`cancelled` / `timed_out` 按下文停止规则处理。单次工具等待返回或调用时限不等于原生 `timed_out`，不据此清除原请求或重置时限。

### 普通滑块仅尝试一次

仅当前任务 owned 页、没有未决人助，且可明确辨认普通拖动条及其起点和终点时，执行者可用当前 BrowserOS 支持的拖动动作尝试一次。拼图、点选、文字/短信验证码、密码、多步或无法确定的验证直接人助；不读取或输入凭据，不调用第三方解题/token服务，不模拟已通过状态，不刷新重试。

优先使用当前快照的元素引用；必须用坐标时，以当前截图/视口定位。窗口分辨率、滚动或页面布局变化后重新定位，不复用旧坐标；跨 iframe 的坐标换算与目标归属须明确，不能确定就转人工，不依赖固定 CSS 或仅 iframe 检测。

拖动前先检查本次阻塞的已有记录。已有任务时，用现有 `incidents` 的 `{ time, type, detail }` 记录意图：`detail` 仍为字符串，写入首次分配并持续沿用的阻塞事件标识、平台、页面URL（不含凭据/令牌）、目标和尝试时间；拖后追加同一标识的实际结果与核验依据。意图落盘后即消耗该事件唯一一次尝试，异常或结果未知也不再拖。刷新、重派、重连不重置标识或次数；仅实际核验恢复正常后又新出现的验证才算新事件。尚无 run 时由唯一 owner 保留同类准备状态，不虚构 run；状态丢失、无法确定是否已试则转人工。恢复执行者必须查记录；`records.mjs` 只保留事件，不内建自动防重复状态机，不能只依赖脚本阻止重试。

拖动完成不等于验证成功：须确认验证区域实际解除，并核原页面、账号/目标及原只读操作恢复正常，才继续原流程；不清除既有未知发送或提交事实。失败或不确定立即转下面的人助，不计入 Hand back 后的两次实际核验失败次数。请求一旦处于 waiting，禁止再拖动或操作受阻页，按原请求等待及核验规则处理。

### 取任务前的人助

取任务准备期间尚无本次目录时（包括用户已给 IQ 编号但尚未取得 run 目录），主代理在本轮会话和 BrowserOS 原请求中保留 owner、requestId、目标标签/网址、状态及核验失败次数，沿用下节的唯一 owner、持续 await 和交回后实际核验要求；不虚构 IQ，不创建业务 run，不执行 `beat` 或 `finish`。人助未解除前不选任务、不派发平台代理。任一次取消或超时，或同一阻塞连续两次实际核验失败，结束本轮准备，不称为某 IQ 或平台已经中断；核验通过才继续选任务。已有本次目录时按下节落盘与恢复。

这里没有独立的本机准备断点机制。会话丢失后，先核实原 owner、原请求状态和目标页面；无法确认旧执行已停或未决请求状态时停止并说明，不盲建第二请求、不宣称已从本机恢复。

### 已有任务目录时

先保存平台断点和请求状态，并行时打 `--paused`。调用前先列标签，确认目标标签属本会话 owned 范围；会话命名、能操作该页或同窗存在该页均不能代替核查。无合适目标时在可用窗口创建任务页或按当前能力恢复归属，不用新窗掩盖登录态问题；无法安全归属时记录阻塞并上报。

1. 发现阻塞的执行者为唯一 owner，创建请求后立即按[人助记录](run-protocol.md#人助记录与解除)保存范围、owner、`requestId`、目标标签/网址、状态、创建时刻和同阻塞事件核验失败次数，并通知主代理。已有未决请求先续接，不另建；共享会话只由一个 owner 消费，其他受影响操作暂停，独立平台继续。
2. 返回 `waiting` 时，owner 留在本轮持续 `await_human_help` 原请求，直至 `resolved`、`cancelled` 或 `timed_out`，不操作受阻页面、不用 final 结束轮次。官方当前默认每个请求总时限为 **20 分钟，自创建起计算**，所有轮次适用；单次返回 `waiting` 不等于超时，继续 await 不重置总时限。此值不是技能配置，不虚构 `timeout` 参数。首次调用已返回终态时直接处理。
3. 用户按 **Hand back** 返回 `resolved` 后，owner 按[逐项检查](#访问限制与逐项检查)自动核验原目标页及原受阻必要步骤是否实际可用；不要求用户回主聊天输入「继续」或「好了」。先保留 `verified:false`，实际阻塞恢复才保存 `verified:true` / `verifiedAt` 并清暂停、重置失败次数，检查原 `deadline` 并先读停机期间的新回复，再继续。仅剩风险信号不妨碍恢复；`resolved` 本身不证明登录/验证成功，也不扩大业务授权。
4. 确认必要流程受阻、无既有可用路径且无可操作验证时，按上节中断，不再申请人助。可操作登录/验证第一次 `resolved` 后核验原阻塞仍未恢复，记录失败次数 1，再申请一次人助；第二次核验仍失败即该平台 `status: "interrupted"`、写 `interruption.reason`，停止该平台本轮执行。次数按同一阻塞事件累计，换请求不重置，只有原阻塞实际恢复才重置。任一次 `timed_out` 或 `cancelled` **立即中断**受影响平台，不自动重试；其他平台继续至结束，本轮停在当前 IQ，不取下一任务。ERP 人助失败只中断 ERP 写回，本地询价可独立完成并留存，批次不继续下一 IQ。
5. owner 仍等待时不重复唤醒。owner 意外空闲时，主代理只续跑原 owner 消费持久化 `requestId`；换 owner 前确认旧执行停止并交接原请求与最新文件，不创建第二请求。用户「停止询价」优先于后到的 `resolved`：停止全部执行及 ERP 写入，保存断点，不自动恢复。

**当前接口的取消错误适配**：人助工具返回 `isError: true` 且 `structuredContent.cancellationKind === "cockpit.operator-cancelled"` 时，已确证当前 BrowserOS 会话被人工取消。保留原始返回结构，将执行分类记为 `cancelled`；原返回没有 `status` 时记 `nativeStatus: null`，并以 `statusSource: "structuredContent.cancellationKind"` 标明分类依据，不补造原生 `status` 或 `timed_out`。未返回请求 ID 时记 `requestId:null`，不 await 不存在的 ID。按第 4 条立即中断受影响平台（ERP 人助仅中断写回），不新建请求、不盲目继续 await、不继续操作该会话页面；其他平台照常完成，本轮停在当前 IQ。只有上述明确结构适用此分类，普通工具错误不能当作人工取消；用户全局停止仍优先，按停止全部执行及 ERP 写入处理。

恢复同 IQ 时先执行 [原 run 恢复与防重复](run-protocol.md#原-run-恢复与防重复)，读取最新平台文件及未决人助。`completed` 不重问；`interrupted` 先按[逐项检查](#访问限制与逐项检查)核实原受阻必要步骤恢复、登录及验证不再阻塞，再按原 binding 只读停止期间的新回复、核对每条未决发送并判断超时，不试其他商品探测。保留 `sentAt`、`followUpAt`、`replyAt`、`followUps`、`answeredTopics`、`thankYou` 和原 `deadline`；跟进等待从 `followUpAt` / `replyAt` 最新时刻起算，超时按店家消息发送时刻判定，不用本次读回或核验时刻重置。缺少答复发送时刻先核聊天证据，无法确认则保持待核、不继续对外发。真实报价即使读取较晚仍可保存本地/草稿；消息本身已过等待时限或店已真正结束时只读提取，不恢复对话、补问或道谢。未知发送结果不能盲重发。

### BrowserOS 会话失效或重连

会话失效先持久化原 run、平台进度、未决发送和人助，不把连接错误当业务超时。明确会话 stopped / no longer active 时，下一次连接调用省略旧 session；连接不可用由主代理按[连接与启动](browseros-setup.md#连接与启动)区分进程未运行与 MCP 故障，必要时启动一次并有界核验，不换浏览器或用新窗口代替恢复。新连接第一步 `tabs action:"list"`，按持久化标签组 ID、任务名、网址及可取得的物理标签标识核实原任务页；已有合适 owned 页就复用，不新建。多个 SDK 句柄可能指向同一物理页，不能只按句柄数认定重复聊天。

当前版本仅 `action:"new"` 携带 `groupId` 能 reclaim，其他 action 传 groupId 不成立；此操作会实际创建页，不是仅恢复归属。正常任务页确实无可复用页、已有页面状态已核清时，才在现有窗口新建一次，必须显式传入已核实的任务 URL，不省略 URL 产生默认 blank；沿用原组还须确认旧 owner 已停止、组确属本任务，并在创建后重列核实 owned、实际 URL 和目标。不为 reclaim 盲建重复聊天，不用读取成功或预览变化证明人助目标已绑定。页面消失原因未明时先核实际库存，不凭失效句柄猜测已经关闭。

仅为当前 API 恢复已核实原任务组的操作归属，且旧 owner 已停止、无未决人助时，可在现有窗口显式调用 `tabs action:"new", groupId:<原组ID>, url:"about:blank"` 创建一张临时 reclaim 页。记录新物理标签标识，立即只关闭刚建的临时页并重列核实原任务页及其新 owned 句柄；无法确认临时页关闭则停止，不追加页面。此为受控 reclaim 的临时步骤，不是正常任务页，不用它申请人助，也不以未验证的临时页导航方案代替。原页仍无法挂接控制时，才按下述受控替换处理。

旧页即使显示 owned、evaluate 可读，仍可能报 `no attached session` 且当前 session 无对应 live 目标，不能当作控制已恢复。仅这种 BrowserOS 控制/归属故障可走受控替换，不因发现验证码或访问限制就换页：

1. 确认旧 owner 已停止、精确旧页归属本任务，且无未决原生人助。先保存原 run/平台进度、账号与 binding、滑块事件意图/结果、未知发送或提交事实和原截止；无 run 时保留同类准备状态，不虚构任务。未知结果保持待核，不借换页重放。
2. 用当前工具正常关闭该精确旧物理页，重新列页确认它确已消失。关闭权限或自动审批拒绝时保留报告，不绕路；无法确认旧页关闭就停止替换，不追加第二张聊天页。
3. 在现有窗口以明确已核实的同任务 URL 新建一次。旧组仍有效才沿用；已消失的组不强求复用，保存工具实际新组，仍恢复原 IQ/run。不得并存两张聊天页，不新开窗口或清除登录。
4. 重列确认新页 owned、URL 正确、snapshot 可用且当前 session 的 live 目标存在；先按[逐项检查](#访问限制与逐项检查)核原受阻必要步骤恢复、登录及验证不再阻塞，再按原 binding 只读核实原账号、接收者、会话及消息归属，检查停机期间新回复。未通过则保持暂停，不发消息或提交。
5. 需要人助时仍核创建后的实际请求目标与提示，按原请求等待和交回核验，不用前端预览代替投递证据。换页不清除原 once 事件、未知结果或 deadline；同一滑块事件仍在时，不获得第二次拖动机会，也不据换页宣称验证通过。

此路径仅替换不可控制页，不保证原物理页能直接重新挂接；换页不能证明登录或验证已恢复。

归属恢复后先核对原人助事件：仍有效且未决的由唯一 owner 续接；明确取消/超时已终态的不再 await。只有用户新一轮启动并完成[恢复核验记录](run-protocol.md#人助记录与解除)，才解除本轮阻塞；仍需登录/验证则在安全归属页申请当前人助。BrowserOS 连接恢复不证明 ERP/电商已登录，也不清除未知发送或提交尝试；ERP 提交已发/未知仍只读 verify 原 payload。

## 打卡与监控

**盯进度**：派发时，主代理给每个平台先打一次卡（`records.mjs beat "<本次目录>" <平台> 已派发`），然后用 `node "<技能目录>/scripts/records.mjs" watch "<本次目录>"` 盯各平台的打卡。`watch` 是本机的一个小程序，不消耗 AI 用量：后台持续运行时每 15 秒看一次，某个平台超过 `subagents.stallMinutes` 分钟没打卡（停下等人处理的不算），或所有执行者都已结束时退出，输出 `result`、`interrupted` 列表及每个平台最后一次打卡在做什么：`stalled` 表示卡住，`finished` 只表示本地记录声明各平台已结束，仍须核验平台 `check`、`merge` 和未决人助/发送状态才判断业务完成；有中断平台但其他平台仍 running/paused 时，result 仍为 `running`，继续等待其他平台；所有执行者已结束且存在中断时，result 为 `interrupted`，本轮结束、只留草稿，不算业务完成，也不按卡住处理。`watch --once` 只检查当时的状态；发现卡住的实际延迟还取决于客户端唤醒和工具调用，不能保证固定时限。仅按本次客户端读取「Claude Code 派发与续跑」或「Codex 派发与续跑」。

`watch` 只检查本地记录和心跳，不消费 BrowserOS 人助状态。主代理被唤醒或检查进度时，也核对已上报且尚为 `waiting` 或结果未确认的请求的 owner 是否仍在执行；owner 意外空闲时按「暂停与恢复」续接，不因 `watch` 没报卡住而遗漏。

## 子代理卡住时

`watch` 报 `stalled` 时先停止该执行者并核实。保留原平台文件及已自然结束店的记录，将平台记 `interrupted`，写明 `interruption.reason`、受影响型号和最后进度；未完成型号写 `incompleteItems`。未完成会话保持可恢复状态，不能以卡住伪造 `endedAt`、`repliesDone`、超时、无货或业务结束。尚无平台文件时保留可核实事实，写空结果及明确中断范围，不补造发送时间。

其他平台继续；完成一个平台就通知主代理按下节代存草稿。当前 IQ 所有执行者结束后保存本地记录和报告，本轮结束，不取下一 IQ、不正式提交。后续用户重新启动当前 IQ 时恢复原 run；本轮不重派询价。

## 合并与记录失败

记录均按[受控保存](run-protocol.md#受控保存与事件)使用目标 scope 的最新 revision；候选输入文件未成功提交前不算生效。CAS 冲突重读合并，pending 由受控写入口恢复；不手工删锁、删日志或覆盖权威 JSON 来消除错误。

**平台完成即存草稿**：平台先持久化关键动作和最终结果、自检通过并通知主代理。主代理是唯一串行 ERP 写入者，执行 `records.mjs merge "<本次目录>" --partial <平台...>` 合并指定已持久快照，再用 `erp-items "<本次目录>/run.json" --draft` 生成已有报价并按 [ERP 协议](erp-api.md#草稿核对提交一次与再核对)存草稿、核对。其他平台继续，不等待全部结束才保存。ERP 不可用仍保留平台文件及待写回结果，不让平台自行写 ERP。

**正式提交守卫**：仅所有平台均真正 `completed` 或用户明确跳过，且平台/ERP 人助都已核验解除，才默认 `merge` 并生成正式输入。暂停、`waiting`、未核验 `resolved`、`interrupted`、卡住/损坏收尾及 `watch finished` 都不证明业务完成。任一平台因人工失败中断时，只能留草稿；其他平台做完后本轮在此 IQ 结束，不取下一任务。ERP 人助未解除时仅保存本地结果/payload，不调用 ERP save。

`merge` 失败时先区分业务字段错误与文件/身份损坏。平台 JSON 可解析、元数据和 runId 归属有效时，可读取最新 revision，依据可核实事实修正完整业务快照，经 `checkpoint` 校验保存，不改报价事实、不恢复询价或发送；新快照仍不合法就保留证据并报告。能合法保存时标 `interrupted` 和明确 `incompleteItems`，不能假写 `skipped` 或补造价格。

平台 JSON 结构、元数据或身份损坏时，`readPart` 本身会拒绝，不能靠 `checkpoint` 重写修复；保留现场交维护者，不手删文件、覆盖身份或重建目录绕过。只有目标平台文件本来不存在时才允许以 revision 0 新建，也须依据实际证据，不删除坏文件冒充缺失。主记录仍合法时，主代理可经主 scope 的 `checkpoint` 在无 platform 的 `incidents` 记录真实平台异常并置 `stopAfterTask:true`；已保存且可校验的其他平台结果可指定 `merge --partial` 留草稿，无法确认的报价不写 ERP。主记录也不可合法保存时保留现有文件、停止依赖动作并报告，不声称中断状态已落盘。本轮不正式提交、不取下一 IQ。

### Claude Code 派发与续跑

- 用 Agent 工具派发，每个平台一个，`subagent_type` 用通用代理（`general-purpose`）。非空的 `subagents.claude.model` 传入 `model`，非空的 `subagents.claude.effort` 传入 `effort`；空字符串不传，沿用默认。让子代理在后台运行，各平台同时进行。
- `prompt` 里写全上文要求的文件绝对路径、任务信息、当前设置和已获授权的范围。子代理看不到主代理的聊天，不能依赖它知道上下文。子代理不再向下派发子代理。
- 记下每个子代理的 ID 和名称与平台的对应关系。子代理在后台运行时，结束或停下都会通知主代理。派发后用 Bash 的后台运行方式执行 `watch`，它退出时也会唤醒主代理；主代理不反复查看进度。被子代理的通知唤醒时 `watch` 还在运行，就不用管它；`watch` 已经退出、还有平台在进行时（如处理完卡住的平台、用户处理好暂停的平台后），再启动一次。
- 子代理需要人处理时按「暂停与恢复」区分：BrowserOS 请求 `waiting` 时，向主代理上报后留在本轮继续 await；发送前业务确认由主代理协调。明确业务确认完成后，或 BrowserOS 请求尚为 `waiting` / 结果未确认且 owner 意外空闲时，主代理用当前客户端可触发续跑的 SendMessage 让原子代理接着做；BrowserOS 请求先消费原请求状态，不提前清除暂停。
- 重新派发或改用单代理前，先确认旧子代理已经结束，还在运行的用 TaskStop 停止并核实。同一平台只能有一个执行者。续跑前读取最新的平台文件，并核对聊天里已经发出的内容，保留发送时间、追问次数和道谢记录，避免重复发送。
- 工具名和参数以当前客户端的实际工具声明为准。指定的模型或思考深度不可用、子代理拿不到 BrowserOS neo 的工具或必要文件时，停止已启动的平台子代理并核实，改用单代理交替推进，说明原因和实际使用的模型。

### Codex 派发与续跑

- 派发前查看当前会话的子代理工具及其参数、可用模型和深度。`settings.json` 是本技能的输入，不是 Codex 的原生配置文件；不要为它修改用户电脑上的全局 `config.toml`。
- 使用 `collaboration.spawn_agent` 时，非空的 `subagents.codex.model` 传入 `model`，非空的 `subagents.codex.effort` 传入 `reasoning_effort`；空字符串不传。显式设置任一项时用 `fork_turns="none"`，把上文要求的文件绝对路径、任务信息、当前设置及已获授权的范围完整写进 `message`，不能依赖子代理继承聊天。`task_name` 包含任务编号、平台和派发轮次，避免与仍存在的代理重名；不再向下派发子代理。
- 记录返回的代理 ID 与平台对应关系。`list_agents` 查看状态，`wait_agent` 等待任意代理的消息或状态变化，每次最多等 60 秒；该工具不接受某个代理句柄作为等待目标，返回的摘要不能代替读取实际消息和平台记录。每次被唤醒或超时，都执行一次 `watch "<本次目录>" --once`，按最后一次实际打卡时间判断，输出 `stalled` 时按「子代理卡住时」处理；同时核对已上报且尚为 `waiting` 或结果未确认的 BrowserOS 请求的 owner 状态，按「暂停与恢复」续接意外空闲的 owner，其余接着等。不能只在超时时检查，也不能因别的平台有消息而重新计算卡住时间。等待超时本身只表示尚未返回，不代表失败。
- 子代理用 `send_message` 向主代理上报需要处理的情况。BrowserOS 请求 `waiting` 时上报后保持本轮 await；业务确认由主代理协调。`send_message` 只投递消息，不触发空闲代理执行：明确业务确认后由主代理 `followup_task`；BrowserOS 请求尚为 `waiting` / 结果未确认且 owner 意外空闲时用 `followup_task` 要求先 await 原请求，保持暂停直到 `resolved` 且页面核验通过，不创建第二请求或第二执行者。
- 重新派发或改用单代理前，先确认旧代理已结束当前执行，必要时用 `interrupt_agent` 中断并用 `list_agents` 核实状态；中断不销毁代理，也不意味着并发容量已释放，派发下个任务前按实际状态和容量检查。同一平台只能有一个执行者。读取最新平台文件并核对聊天中已经发出的内容再续跑，保留发送时间、追问次数和道谢记录，避免中断后重复发送。
- 当前客户端若提供其他工具名，以实际工具声明中的派发、等待、停止、续跑能力为准，不调用不存在的接口。指定模型或深度不可用、工具不支持设置它们、并发名额不足，或子代理无法访问必要文件及 BrowserOS neo 时，停止已启动的平台代理并核实状态，改用主代理单代理交替推进，说明原因与实际使用的模型；不能确认旧代理已停止时，暂停受影响平台，不重复接管。

### 单代理交替推进

主代理自己完成全部步骤，也统一写 `run-<平台>.json`，由合并更新主文件；一个平台完成就串行代存草稿。[挑店与会话](inquiry-rules.md#8-执行挑店与会话)在各启用平台交替进行：`confirmBeforeSend` 为 `false` 时，**哪个平台先挑完本任务所有型号的店，就先开始给它发询价**，同时继续挑其他平台的店；为 `true` 时，先汇总所有未跳过平台的店铺和话术，得到一次明确确认后再发送。之后每一轮轮流查看各平台的聊天页。

## 收尾

1. 按[共享浏览器](#共享浏览器)规则核实并清理本轮任务标签。自己的 ERP 标签页留着给下一个任务用，全部结束时再按同一规则清理。
2. 按 [run-protocol.md「任务汇报」](run-protocol.md#任务汇报)向用户汇报，并按该文件「实跑报告」写报告；发现新的页面情况按该文件「本机经验」记录。

收尾、中断与原 run 恢复均保存对应关键事件和已知阶段时间；`finish` 只归档现有事实，不补齐未执行阶段。耗时以真实起止和等待记录为依据，未知区间明确缺数据，完整口径见[时间线与耗时](run-protocol.md#每日时间线与关键事件)。

## 停止或继续

1. 指定编号只做当前 IQ。批量只有当前任务正常完成（或按业务内容问题转人工且未发生平台中断）、本地 `finish`、报告和汇报完成后才取下一项。`stopAfterTask` 为 `true` 时不调用 `next`，即使其他平台正常完成也一样；新一轮用户启动并核实恢复条件后才可清除本轮停止标记。
2. 主代理维护仅本轮有效的已收尾业务 `manual` 任务集合：只有符合第 1 条继续条件且完成 `finish`、报告和汇报后才加入。每次调用 `next` 前，从最新 ERP 待处理列表中过滤该集合，再按剩余原顺序传候选，避免本轮立即重选同一未提交 run。集合不写成 `skip`、不删除原断点；用户新一轮启动时清空，仍按完整待处理列表恢复原 run。`stopAfterTask` 或第 3 条停止边界优先，不得借过滤集合继续批次。`next` 如返回 `resumeRun`，恢复其原目录，不新建覆盖。已提交、已跳过以及没有可恢复未完 run 的转人工任务不自动重做。每次换任务前确认上一任务执行者已停止。
3. 平台必要流程受阻、无既有可用路径且无可操作验证可处理、BrowserOS 人助核验连续两次失败、任一次人助 `cancelled` / `timed_out`、平台卡住/记录损坏：只中断受影响平台，其他平台继续至结束，可代存草稿；本轮停在该 IQ，不正式提交、不取下一 IQ。风险信号未影响必要步骤时照常执行，不因此设置 `interrupted`、未解除的人助或 `stopAfterTask`，不新增只留草稿限制。ERP 登录失败只暂停写回，其他平台完成本地结果；ERP 整体故障同样保留本地结果并停止批次，接口合同错误不再调用 ERP、不猜字段。聊天提问的无答、关闭或取消范围按[主代理提问与续跑](#主代理提问与续跑)处理。
4. 用户说「停止询价」或「停」：立即停止所有执行者和等待，核实停止后读取最新文件，保留可恢复断点并部分合并、幂等 `finish`、报告和汇报；不再发商家消息或调用 ERP 写入，不补造未完店的 `endedAt`、`repliesDone`、无货或发送事实。迟到的人助交回不恢复执行。
5. 保留数据中的同一 IQ 后续重新启动先按 [恢复协议](run-protocol.md#原-run-恢复与防重复)核对原 run、聊天证据和 ERP 持久化基线。已完成平台只补写回，未完成平台继续原进度，不自动后台续跑；跨版本数据保留及旧格式清理边界见[数据生命周期](data-lifecycle.md)。
6. 全部结束或本轮停止时总汇报：已完成/已提交的任务、跳过原因、需人工处理的当前 IQ、各平台完成或中断状态、草稿保存/待写回/提交结果未确认、断点位置和本轮结束原因。随后关闭本次可安全关闭的标签，保留用户和其他任务标签；未决人助先按当前工具交接/结束，不能丢弃归属与请求记录。

## 故障速查

| 情况 | 处理 |
|---|---|
| BrowserOS neo 连不上 | 主代理按[连接与启动](browseros-setup.md#连接与启动)检查 MCP、窗口/标签与可靠进程证据；确认未运行才按真实入口启动一次并最多等待 120 秒；已运行先恢复连接，确需人工时说明具体原因 |
| 风险提示、没登录、验证、账号异常或访问限制 | 按「暂停与恢复」核必要步骤实际可用性；仅有风险信号时继续原流程，实际阻塞才暂停/中断。普通滑块仅可先尝试一次，其余可操作验证请求人助；必要流程受阻、无既有可用路径且无可操作验证时中断，不循环人助。只影响对应平台，ERP 出问题只暂停写回；不记无货 |
| `erpApi` 返回 `ERP_CONTRACT` | 立即停止 ERP 调用；独立平台继续保存本地结果，本轮不取下一 IQ。提示用户「ERP 接口已修改，烛龙智能询价没有同步，请更新技能」，把 `problems` 写进汇报和实跑报告（见 [erp-api.md「ERP 错误与重试边界」](erp-api.md#erp-错误与重试边界)） |
| `erpApi` 调用不到 | 按[域注册流程](browseros-setup.md#按域注册与核验-helper)核实 ERP 地址/页域、运行时清单，按需从技能源码适配并 `saveHelper`；下一次 `run` 实际调用 `ping`，不以磁盘复制代替加载验证 |
| 聊天页「连接断开」 | 按[会话失效或重连](#browseros-会话失效或重连)核归属、优先复用并保留原 binding 和断点；仅满足受控替换条件时换页，不动用户或其他任务页 |
| 平台弹出需要选择的账号设置（如聊天工具） | 按「暂停与恢复」交用户处理浏览器页面；不以聊天输入框代替接管 |
| 子代理卡住（`watch` 输出 `stalled`） | 按「子代理卡住时」处理：停掉它，保存 interrupted 断点，其他平台继续，留草稿、不提交、不取下一 IQ |
| 合并失败（`merge` 报错） | 按本文「合并与记录失败」区分：可读且身份有效的业务字段错误经 checkpoint 校验修复；JSON/元数据/身份损坏保留现场交维护者，不覆盖重写；主记录合法时保存真实异常与 stopAfterTask，保留其他有效平台结果 |
| 子代理报错返回、中途出错 | 先查代理状态；等待超时不等于失败。确认原代理停止后，读取 `run-<平台>.json` 并核对已发送消息，再恢复原代理或重派；无法确认停止则暂停该平台，仍失败时保存 interrupted 断点并说明，不假写业务完成 |
| 所用的 AI 派发子代理失败 | 先停止并核实已启动的平台代理，读取已有进度后改用单代理交替推进，在汇报里说明；无法确认停止的平台不重复接管 |
| 站点脚本调用不到 | 按[域注册流程](browseros-setup.md#按域注册与核验-helper)仅核对本次相关域的实际源码；已知旧官方自动同步，未知本机差异保留报告；注册后下一次独立 `run` 读回 hash 并只读调用核验，不以停用域缺失阻塞本次；必要时按平台明文步骤操作 |
| 草稿/提交回价失败 | 按 [erp-api.md「ERP 错误与重试边界」](erp-api.md#erp-错误与重试边界)处理：只读请求或明确 writeAttempted:false 的 save 可按原限额重试；已发/未知 save（含草稿）只用原 payload 和原基线 verify，登录恢复不授权重放；正式提交仅明确 not_sent 可修复后用原 payload 重试，不凭错误名判断 |
| 型号已报给客户（只读） | 跳过该型号，汇报里说明 |
